# rpc-stacks coverage

Ports of `apps/extension/tests/specs/rpc-sip30-requests`, plus the `rpc-policy-propose` and `policy-surfaces` specs, which have no mobile equivalent.

Every flow runs `shared/start.yaml`: new wallet with the `rpc-stacks` scenario (contract interfaces for bns, leo-token and living-leather, LEO token metadata), the test dApp from `TEST_APP_URL` in the Browser tab, connected with Load account. A flow then taps one card from `apps/test-app/src/methods/mobile-e2e-stacks.ts` (category Mobile E2E, shown with `VITE_TEST_APP_MOBILE_E2E=true`), checks the approver, approves or cancels, and asserts the card verdict `PASS`. Cancel cards expect error 4001, so `PASS` means the wallet returned 4001.

Keys are random, so the extension's fixed signatures and public keys cannot be asserted. The approve cards verify instead. Message signatures recover to the returned public key, which must equal the account's STX key read by the `e2e stx warm addresses` card. The multisig answer adds exactly one signature field, that signature recovers over the transaction sighash to the account's key, and the rest of the transaction is unchanged. The SIP-30 single-sig answer keeps the recipient, amount, memo and nonce, and its signature recovers to the account's key. The returned STX transfer pays the requested recipient, amount and memo, its signature recovers to the account's key, and it matches its txid.
